CIM Model Exchange in a Global Grid

Embracing variation without losing semantic meaning — illustrated with conceptual CIM abstraction diagrams.

CIM / IEC 61970 CGMES TSO/DSO Interoperability Consultation Paper

Executive Summary

The IEC Common Information Model (CIM) is widely used to exchange power system model information across organisations and tools. A defining feature of CIM‑based exchange is the ability to support multiple valid representations of the same physical assets, depending on context (operations, planning, regulatory reporting, or coordination studies).

This article frames a pragmatic approach: preserve identity semantics (mRID), use profile‑based scoping for exchanges, and make abstraction assumptions explicit so that recipients can interpret the model correctly. It closes with open questions for global industry deliberation.

1) Identity‑centric modeling

CIM anchors interoperability on shared semantics and persistent identity (commonly via mRID), rather than requiring identical internal representations. This enables different utilities to represent the same physical asset differently (e.g., transformer abstractions) while remaining interoperable—provided identity meaning is not changed.

Practical implication: treat mRID governance as a shared contract; abstractions can differ, but identity semantics should not.

2) Topology abstraction

Substation topology may be maintained as node‑breaker internally (to preserve switching detail) while exchanged as bus‑branch for coordination studies. The abstraction level should be aligned to the exchange purpose and explicitly documented.

When switching detail is required (e.g., certain operational studies), agree profiles and validation accordingly.

3) Boundary exchange vs internal detail

Boundary exchanges often share only what is required: identity, connectivity, and minimum parameters. Internal models remain richer and tool‑specific. Profiles define the scope; recipients should not assume omitted detail.

4) Profile‑based exchange pipeline

Interoperability is operationalized through contextual profiles and constraints derived from the CIM base model. Constraint artifacts (e.g., RDFS/SHACL) help validate that exchanged instance data remains within agreed scope and semantics.

5) Open questions for industry consultation

  • Abstraction limits: How much simplification is acceptable before operational meaning is lost?
  • Identity: Should the same physical asset always retain the same mRID across abstraction levels?
  • Reduced‑order profiles: Do we need globally standardized reduced‑order / boundary profiles?
  • Transparency: Should modeling assumptions be machine‑readable, not just human‑documented?
  • Accountability: Who bears responsibility for preventing semantic misinterpretation—sender, receiver, or shared governance?
